# Rebuild FinalGitGraph as a verifiable topological log

The current FinalGitGraph backend loses graph edges in its default code path. That one bug shows the architecture's DNA. gix walks history newest-first. LMDB stores everything in 17 string-keyed tables. A whole-blob CSR graph is patched once per 16,384-commit write wave, and any parent that arrives in a later wave is silently skipped (`db.rs:2657-2659`). On any repository larger than one wave, BFS from HEAD stops after about 16,384 commits and `shortest_path(HEAD, root)` returns `found=false`, with no error. Every gate misses this. The only edge assertion compares stored metadata with itself. Every test fixture has 3 commits. The perf harness throws away its query results. The "performance budget" gate times nothing. The gates also cannot run on macOS or Linux, because every script calls the Windows-only `powershell` command. The replacement should number commits parent-first (each parent ID is lower than its child's ID), so an unresolved edge cannot exist by construction. It should store the graph and per-commit columns in immutable, checksummed layer files, merged geometrically the way git merges its split commit-graph chain, and publish them by atomic manifest rename. It should drop LMDB entirely, because v1 needs no key-value engine. It should replace about 37 `GITGRAPH_*` environment toggles with a typed config, and replace 4,191 lines of PowerShell with a `cargo xtask` that behaves the same on Windows, macOS and Linux. Correctness is anchored by differential tests against `git rev-list --parents`, and by metamorphic tests asserting that batch size, thread count, ingest path and OS never change a content digest. None of the data structures is new: git, Sapling, jj and Mononoke already ship them. The only defensible novelty is the verification contract. The ≥100k commits/s target is realistic for topology and metadata, which git walks at about 413k commits/s on one core. It is not realistic for full change sets, which git computes at about 19k commits/s per core. The plan starts with a failing 20,000-commit regression test, then deletes the streaming-CSR path. Nothing in this report was compiled, run or benchmarked inside the repo.

## The DNA: a mutable graph blob, numbered newest-first, steered by ambient switches

FinalGitGraph is a Rust library and CLI (`apps/desktop/src-tauri`, about 11.2k lines in `adapters/` and `application/`). It copies a local repository's commits into LMDB, keeps a compressed-sparse-row (CSR) parent/child graph, answers commit-window, BFS/DFS/topological and shortest-path queries, and extracts per-commit file changes in the background. It pins `gix = "0.80.0"`, `gix-pack = "0.67.0"`, `lmdb = "0.8.0"`, `bincode = "1.3.3"` and `rayon = "1.11.0"`, and `rust-toolchain.toml` pins Rust 1.94.0 with `targets = ["x86_64-pc-windows-msvc"]`. The diagram below traces one full index from the gate scripts to a query. Paths are relative to `apps/desktop/src-tauri/src/` unless stated otherwise.

The design has five traits, and they reinforce each other. **The first is ordering.** Commits are identified by committer time, newest first, and the walk emits children before parents. Committer time is not a topological order on real repositories with clock skew, which is why git introduced corrected commit dates ([GitHub: Git's database internals II](https://github.blog/open-source/git/gits-database-internals-ii-commit-history-queries/)). The incremental checkpoint is built on the same clock: it resumes from the maximum committer time minus a 300-second lookback (`indexer.rs:367-369`). That is a heuristic, not a sound frontier. **The second is a mutable whole graph inside a key-value store.** The CSR is one bincode blob per repo, rewritten on every wave. Four functions build it, across three update paths (full rebuild, per-wave delta, overlay): `rebuild_csr_snapshot` (`db.rs:1482`), `apply_csr_delta_from_commit_shas` (`db.rs:1577`), `persist_graph_overlay_commits` (`db.rs:1643`) and `build_incremental_csr_snapshot` (`db.rs:2600`). Only the paths that see every commit at once are correct across waves. **The third is query-by-hydration.** Each command reopens the LMDB environment and inflates the graph into a `HashMap<String, usize>`. By arithmetic estimate (String header, 40-byte hex allocation, bucket and load-factor slack), that costs about 85–100 bytes per commit, or roughly 1 GB at 10M commits. **The fourth is behavior steered by ambient environment variables.** There are 37 distinct `GITGRAPH_*` names across Rust, scripts and config (40 if CI YAML is counted). Rust reads 32 of them at runtime, and at least 8 are set by scripts but read nowhere. **The fifth is governance by string matching on Windows.** The gates run Windows PowerShell, the guardrail script checks that function names exist rather than what they do, and the paths are Windows-first, such as `D:\temp\gitgraph-lab`.

Several parts of this DNA are sound and should survive. A single writer feeding bounded Rayon compute (ADR 0007) is the right concurrency shape for a desktop indexer. Extracting file changes asynchronously, off the critical path, matches how Mononoke keeps derived data out of the commit path: "Derived data computation is not on this critical path" ([Mononoke derived data](https://github.com/facebook/sapling/blob/main/eden/mononoke/docs/2.3-derived-data.md)). Reading git's commit-graph through gix (`walk_commits_from_commit_graph`, `git.rs:1196`) is the right fast path for topology. The "metadata by default, line stats lazily" policy matches the cost profile measured in git itself (see the throughput section). The problem is not the ambition. Ordering, mutability and ambient configuration multiply the number of places an edge can be lost, and the tests never cross the boundaries where that happens.

## Ranked loopholes: the default path loses edges and every gate stays green

### The edge loss is confirmed by reading the default path

The bug sits in the configuration every user gets. `GITGRAPH_LEVEL3_STREAMING_CSR` defaults to true (`indexer.rs:372`). The streaming mode defaults to `FullPlusIncremental` (`indexer.rs:1453-1461`). So `streaming_snapshot_apply_enabled_for_mode` returns true for both full and incremental runs (`indexer.rs:1464-1475`). After each wave is persisted, the indexer calls `store.apply_csr_delta_from_commit_shas(repo_id, &batch_shas)` (`indexer.rs:1595-1606`). Inside the delta builder, a parent that is not yet in `sha_to_index` is dropped with `let Some(&parent_index) = sha_to_index.get(parent_sha) else { continue; };` (`db.rs:2657-2659`). The walk emits children before parents, so the oldest commit of wave 1 always references a parent that only arrives in wave 2. Once streaming apply has materialized anything, the final full rebuild is skipped, because the rebuild runs only when `!streaming_snapshot_apply_enabled || !streaming_csr_materialized_any` (`indexer.rs:743`). Nothing ever re-adds the dropped link.

The perf showcase does not exercise this path. Under `-HardwareMax`, `scripts/perf-report.ps1:464-470` sets `GITGRAPH_LEVEL3_STREAMING_CSR = "0"`, forces `GITGRAPH_COMMIT_WALK_SORT = "breadth_first"`, and sets a `throughput` write profile that no Rust code reads. The "100k hardware ingestion fast path" in the recent commit history therefore measures a configuration users never run. The repair already exists in-tree: build the graph once after the walk with `rebuild_csr_snapshot` (`indexer.rs:797-806`), as the hardware lane does per ADR 0018, and use the overlay path for incremental runs. Its compaction passes all overlay commits in one call, so links resolve (`indexer.rs:742-780`).

### Why no gate noticed

The test suite cannot see edges. The smoke test asserts `snapshot_metadata.directed_edges == counts.1` (`tests/indexer_smoke.rs:85`), but `counts.1` comes from `load_dataset_counts`, which reads the same snapshot metadata (`db.rs:1884-1890`). The assertion is a tautology. Every smoke repo has 3 commits, below the smallest batch of 2,048, so no test crosses a wave boundary. The perf harness discards every traversal and shortest-path result with `let _ =` (`bin/perf-report.rs:266-301`). The `quality:perf` gate runs one functional test, `lmdb_index_and_graph_queries_work_end_to_end`, and checks only that it passed (`scripts/perf-budget.ps1:237-247`). BFS could become 100 times slower and that gate would stay green. Meanwhile `enforce-guardrails.ps1` requires the names `walk_commits_tape` and `rebuild_csr_snapshot` to exist (`:280-287`, `:424-428`, `:462-466`). It even forced a constant, `PATCH_FROM_DIFF_GUARDRAIL_MARKER`, whose only use is `let _ = PATCH_FROM_DIFF_GUARDRAIL_MARKER;` (`git.rs:67`, `:4037`). The bug passes every guardrail. A correct rename would fail them.

The commit-graph "will not be read or written when replace-objects or grafts are present" or when shallow commits are present ([git commit-graph design](https://git-scm.com/docs/commit-graph)). The research found no such guard in the fast path, but this was inferred, not verified line by line.

### Identity: a dense parent-first integer makes the bug unrepresentable

The most important change is to assign every commit a dense u32 ID in parent-first topological order. Each ID is issued only after all its parents have IDs, so every parent ID is lower than its child's. This is the invariant behind Sapling's IdDag, where "Ids are topologically sorted" and every segment's parents sit below its low end ([sapling-dag iddag.rs](https://docs.rs/sapling-dag/latest/src/dag/iddag.rs.html)). jj's index files are likewise written "in some topological order with parents first", with parents stored as global positions ([jj-lib readonly.rs](https://docs.rs/jj-lib/latest/src/jj_lib/default_index/readonly.rs.html)). Under this contract the edge-loss class disappears rather than being patched. When a child is sealed, every parent already has an ID. A parent that is truly absent, such as a shallow boundary or a missing object, becomes a typed boundary record, never a `continue`. Assignment uses an iterative DFS from the tips that visits the first parent last, so first-parent chains get contiguous IDs. Most parent hops then become `i -> i-1`, which is the best case for prefetching and column scans. Git's own commit-graph positions follow OID-sorted order, not topological order ([gitformat-commit-graph](https://git-scm.com/docs/gitformat-commit-graph)). So the commit-graph serves as a fast topology input, and the engine renumbers its output instead of adopting git's positions as IDs. Software Heritage made the same move when it renumbered nodes to restore locality ([SANER 2020 slides](https://upsilon.cc/~zack/talks/2020/2020-02-19-saner-graph.pdf)). OIDs are stored as binary with a per-repo object-format tag, 20 or 32 bytes, so SHA-256 repos need no schema change.

### Storage: checksummed layer files replace all 17 LMDB tables

The graph needs no key-value engine, because it is append-only by construction. With parent-first IDs, a commit's parent row is complete when the commit is inserted, and new IDs are always the maximum. The design therefore copies git's split commit-graph chain. Layer files are named by content hash, a small chain file lists them, positions are cumulative across layers, and a layer merges down when "the number of commits in level N is less than X times the number of commits in level N + 1" (default X = 2) or when it exceeds a max-commits cap. That rule keeps the number of layers logarithmic ([git commit-graph design](https://git-scm.com/docs/commit-graph)). Each ingest wave writes one new top layer of about 16k–64k commits, so a wave costs O(wave) instead of O(total). The research notes estimate the effect at 10M commits. Today's 16,384-commit waves cause about 625 whole-blob rewrites averaging about 180 MB, roughly **110 GB written**. A chain with size multiple 2 rewrites each commit about 9–10 times, roughly **3.5 GB**. These are arithmetic estimates, not measurements. Tantivy shows the same pattern at scale in search: immutable segments, a `meta.json` "updated atomically", and Searchers that hold a snapshot list of segment readers that commits and merges never disturb ([Tantivy ARCHITECTURE.md](https://github.com/quickwit-oss/tantivy/blob/main/ARCHITECTURE.md)). General dynamic graph stores are the wrong tool. A 2025 benchmark found Aspen using "3.3-10.8x more memory than CSR", and contiguous CSR storage wins on read-heavy workloads ([Su et al. 2025](https://export.arxiv.org/abs/2502.10959)).

The layer format follows git's chunk design with two changes. It has a header (magic, format version, hash kind, endianness marker, chunk count) and a chunk table of `[u32 id, u64 offset]`, and readers skip unknown chunk IDs. Git's lesson from shipping bad generation data stands: a changed meaning gets a new chunk ID, as `GDA2` replaced `GDAT` ([gitformat-commit-graph](https://git-scm.com/docs/gitformat-commit-graph)). The first change is byte order. Git uses network byte order, while this format uses fixed little-endian with every chunk aligned to 64 bytes, following Arrow's alignment advice ([Arrow columnar format](https://arrow.apache.org/docs/format/Columnar.html)). Every target in scope (x86_64 and arm64 on all three OSes) is little-endian, so `&[u32]` views cost nothing through safe `bytemuck`/`zerocopy` casts. One research note proposed big-endian. Either order is equally deterministic, so the cheaper one wins. The second change is a checksum on every layer: an xxh3 trailer, plus per-chunk checksums when cheap. The chunks carry a 256-entry OID fanout, sorted OIDs, an OID-to-ID permutation, parent arrays in global IDs with an overflow list for octopus merges, topological level, corrected commit date, commit time, interned author IDs and a subject string heap. Author and subject columns move out of per-key tables. The 61-byte string keys `"{repo_id:020}:{sha}"` and bincode values leave the hot path entirely.

Publishing uses only `std`, with the same semantics on every OS. The writer writes `seg-<gen>.tmp`, calls `File::sync_all`, renames it to `seg-<hash>.seg`, then writes and syncs `MANIFEST.lock` and renames it over `MANIFEST` (git's lockfile protocol ([git lockfile.h](https://raw.githubusercontent.com/git/git/master/lockfile.h))). Rust's `sync_all` already issues `F_FULLFSYNC` on Apple targets and `FlushFileBuffers` on Windows ([rust std unix fs](https://github.com/rust-lang/rust/blob/master/library/std/src/sys/fs/unix.rs), [rust std windows fs](https://github.com/rust-lang/rust/blob/master/library/std/src/sys/fs/windows.rs)). Its Windows `rename` uses POSIX-semantics `FileRenameInfoEx` with replace-if-exists ([rust std windows fs](https://github.com/rust-lang/rust/blob/master/library/std/src/sys/fs/windows.rs)). Only the small manifest is ever replaced, and readers read it and close it. A segment name is never reused, so a reader never holds a file that a writer is replacing. That is what Windows needs, because a mapped file cannot be renamed over or truncated ([JDK-4724038](https://bugs.openjdk.org/browse/JDK-4724038), [SQLite check-in](https://www.sqlite.org/src/info/75a85a1c6ac59f2d)). The index is a rebuildable cache of git, so the design aims for atomicity and detectability rather than strict durability. On open, the engine verifies checksums. If verification fails, it falls back to `MANIFEST.prev`, and if that fails too, it rebuilds from git. Correctness then rests on "rename is atomic or detectably not". This matters because crash behavior varies widely across file systems: ALICE found 60 crash vulnerabilities in 11 widely used systems ([Pillai et al., OSDI'14](https://www.usenix.org/conference/osdi14/technical-sessions/presentation/pillai)). A full re-index becomes blue/green: build generation N+1 next to N and swap the manifest. That replaces today's "clear all data first".

Layers are read with `read()` into an aligned heap buffer by default, not memory-mapped. File-backed mmap constructors are `unsafe` because external modification is undefined behavior ([memmap2 docs](https://docs.rs/memmap2/latest/memmap2/struct.Mmap.html)). redb removed its mmap backend because soundness was "infeasible to prove", and lost at most about 2x ([redb CHANGELOG](https://github.com/cberner/redb/blob/master/CHANGELOG.md)). The engine already keeps the whole CSR in memory, so lazy paging buys little. By estimate, a 10M-commit topology layer set of about 360 MB is one sequential read. mmap stays an opt-in for larger-than-RAM repos behind its own ADR and kill criterion.

v1 needs no embedded database at all. Once derived work is a set difference (next section), the retry queue disappears. What remains mutable is the manifest (ref tips, layer list, derived-type versions, schema version) and a tiny repo registry, and both fit atomic-rename files. This choice goes further than the research notes, which recommend redb for mutable state: it is pure Rust, ACID, with no mmap ([redb README](https://github.com/cberner/redb)). redb fixed "a critical bug ... This could cause data loss" in April 2026 and lost-commit and page-cache bugs in October 2026 ([redb CHANGELOG](https://github.com/cberner/redb/blob/master/CHANGELOG.md)). So redb (pinned ≥4.4.0) is the fallback, not the default. It gets added only when a mutable record set outgrows a manifest file. SQLite in WAL mode is the alternative if its longer crash record matters more than a C build step ([SQLite WAL](https://www.sqlite.org/wal.html)). In practice the C toolchain is present wherever Rust links on all three OSes, so "pure Rust" mainly buys fewer build scripts and faster cold builds.

The `Engine` owns exactly one writer, taken by `File::try_lock` on `index_dir/WRITER.lock`. That uses `flock` on Unix and `LockFileEx` on Windows, is stable since Rust 1.89, and is released by the kernel on crash ([std::fs::File](https://doc.rust-lang.org/std/fs/struct.File.html)). Other processes (a second app window, the CLI) open read-only snapshots from the same files without a daemon. In-process readers `load()` an `ArcSwap<Snapshot>`. ArcSwap avoids the `RwLock` problem where "an update may be blocked for arbitrary long time by a steady inflow of readers" ([arc-swap docs](https://docs.rs/arc-swap/latest/arc_swap/)). The index lives in the OS cache directory (`~/Library/Caches/<id>`, `$XDG_CACHE_HOME/<id>`, `{FOLDERID_LocalAppData}/<id>`), never in the CWD ([Tauri v2 path API](https://v2.tauri.app/reference/javascript/api/namespacepath/), [directories-rs](https://github.com/dirs-dev/directories-rs)).

### Queries: ID order replaces hydration

With parent-first IDs, most graph questions become arithmetic or a sequential scan. Here, "B reaches A" means A is an ancestor of B. `is_ancestor(A, B)` runs a cascade, cheapest first. If `id(A) > id(B)`, B cannot reach A (O(1), free from the numbering). If `gen_level(A) >= gen_level(B)` and A ≠ B, B cannot reach A (O(1)). If A and B lie on the same contiguous first-parent run, the answer is true. Otherwise a generation-pruned walk runs. That walk is git's proven fallback: it took `git merge-base --is-ancestor v5.0 v5.19` on Linux from 2.64 s to 0.02 s ([GitHub: Git's database internals II](https://github.blog/open-source/git/gits-database-internals-ii-commit-history-queries/)). Topological streaming with a limit becomes "iterate descending IDs over the visible set", with no in-degree pass or heap. That replaces the whole-graph allocation per call (`indexer.rs:2254`). Git needed three interleaved walks to get `--topo-order -n 100` from 6.88 s to 0.02 s on Linux ([GitHub blog II](https://github.blog/open-source/git/gits-database-internals-ii-commit-history-queries/)). `A..B`, `A...B` and merge-base become set algebra over ID bitsets (1.25 MB per 10M commits) or span lists. Shortest path runs as a bidirectional BFS restricted to the ID interval `[id(B), id(A)]` and to generation bounds. OID lookup uses the fanout plus binary search: about 24 bytes per commit for sorted OIDs plus permutation, against an estimated 85–100 bytes for the current `HashMap<String, usize>`. Small queries use a hash map sized to their visit budget, so `max_nodes=10` never allocates a 10M-entry array. Every API takes a budget, returns partial results deterministically, and checks a cancellation token every few thousand nodes. Sapling-style hierarchical segments, which give ancestry in "O(number-of-merges) time" at tens of millions of commits ([Meta Engineering](https://engineering.fb.com/2022/11/15/open-source/sapling-source-control-scalable/)), are a later accelerator gated on a measured segments-per-commit ratio. Heavy 2-hop reachability indexes are rejected: pruned landmark labeling reached 4.4 GB and up to 2.6 h to build on the O'Reach benchmarks ([O'Reach](https://ar5iv.labs.arxiv.org/html/2008.10932)).

### Derived data and incrementality: set differences, not retry queues

Per-commit facts become Mononoke-style derived data. "Information computed from Bonsai changesets ... that can always be regenerated", derived parents-first and versioned per type ("Blame → Blame V2") ([Mononoke derived data](https://github.com/facebook/sapling/blob/main/eden/mononoke/docs/2.3-derived-data.md)). A git commit ID already hashes its tree and all its ancestors. So any fact about a commit's history can be keyed by `(commit, fact_version)` and never invalidated. In build-system terms it is a deep constructive trace ([Build Systems à la Carte](https://www.microsoft.com/en-us/research/uploads/prod/2018/03/build-systems-a-la-carte.pdf)). The first-parent change set becomes the derived type `fc@v1`. Rayon workers compute it and seal it into change layers that cover ID ranges. Pending work is "indexed IDs minus IDs covered by `fc@v1`", recomputed at startup. That deletes the LMDB enrichment queue, the due index (item 8) and the delete-extract-save triple (item 5), because derivation is idempotent and a crash at any point is harmless. A commit whose objects are missing (partial clone, gc'd objects) gets an explicit `unavailable` status in the layer, never a fabricated empty diff. Gitlinks (mode 160000) are recorded as "submodule pointer moved". Renames follow a tiered policy. Exact renames, where a deleted blob OID equals an added one, are deterministic and included. Similarity renames are bounded, versioned and best-effort, because gix "uses the first-found candidate rather than Git's up-to-four candidates" ([gix crate-status](https://github.com/GitoxideLabs/gitoxide/blob/main/crate-status.md)). Line counts come lazily from gix's `line_counts()`, which builds no patch and returns `None` for binary ([gix blob diff Platform](https://docs.rs/gix/latest/gix/object/blob/diff/struct.Platform.html)), using imara-diff's Histogram, "10% - 100%" faster than Myers ([imara-diff](https://github.com/pascalkuthe/imara-diff)). The custom Bloom/murmur3 reader is deleted. Exact change layers answer `log -- path` with no false positives, and v1 filters "have a bug that appears when char is signed" ([gitformat-commit-graph](https://git-scm.com/docs/gitformat-commit-graph)).

Incremental runs diff ref snapshots instead of trusting clocks. The manifest stores `{ref -> oid}`. A run reads the current refs, walks from new tips until it reaches already-indexed OIDs, and appends IDs. This is git's `rev-list NEW --not OLD` semantics, and jj's operation-log view model ([jj concurrency](https://docs.jj-vcs.dev/latest/technical/concurrency/)). Force-pushed-away commits keep their per-OID data and drop out of the visible set computed from current tips, so re-pushing the same OIDs costs nothing. Only the ref layer is non-monotonic. If aggregate views (per-author counts, per-path churn) arrive later, they take DBSP's Z-set delta algebra, where linear operators equal their own incremental versions ([DBSP, PVLDB 2023](https://www.vldb.org/pvldb/vol16/p1601-budiu.pdf)). The algebra is borrowed, the engine is not embedded. Repos that gix cannot fully read, such as reftable repos, are detected and handled with one `git for-each-ref` per refresh, or a clear error ([gix crate-status](https://github.com/GitoxideLabs/gitoxide/blob/main/crate-status.md)).

### Throughput: topology clears 100k commits/s; tree diffs set the ceiling

The ≥100k commits/s target needs a precise definition, because the work types differ by two orders of magnitude. The table below comes from single runs of git's own primitives in this research, on a bare clone of git.git (85,936 commits) with Apple Git 2.39.5 on an M1 Pro. The figures are single-threaded and order-of-magnitude only.

| git primitive (single thread) | Time | Throughput |
|---|---|---|
| `rev-list --all --parents`, with commit-graph | 0.208 s | ≈413k commits/s |
| same, `core.commitGraph=false` | 0.706 s | ≈122k commits/s |
| `log --all --format='%H %P %T %an %ae %at %ct %s'` | 0.799 s | ≈107k commits/s |
| `log --all --raw --no-renames` (non-merge diffs) | 3.402 s | ≈18.9k diffs/s |
| `log --all --numstat --no-renames` | 23.776 s | ≈2.7k diffs/s |

Topology plus metadata can clear 100k commits/s on one core when a commit-graph exists, and on a few cores when one does not. The target should therefore mean "commits per second until queryable topology and metadata are published". First-parent change sets are a separate derived-throughput metric. They need about 6 or more cores at git-like efficiency, a tree-pair cache, or both, to reach 100k commits/s. Line stats stay lazy, because they run at only a few thousand commits per second per core. For larger trees such as linux.git, the per-commit diff cost will be higher, and that is unmeasured. Moving gix from 0.80 to the current 0.9x line brings parallel `gix-pack` and the order-independent rename-tracker fix ([gix CHANGELOG](https://github.com/GitoxideLabs/gitoxide/blob/main/gix/CHANGELOG.md)). The custom pack "tape" walker (ADR 0017) is kept only if a digest-checked benchmark shows it beating gix-odb's per-thread caches.

## Proof against real git, identical on three operating systems, zero leftovers

### One command: cargo xtask replaces pnpm, PowerShell and Docker

The Rust ecosystem settled this already. A workspace `xtask` binary with `xtask = "run --package xtask --"` in `.cargo/config.toml` "doesn't require any other binaries besides `cargo` and `rustc`" ([cargo-xtask](https://github.com/matklad/cargo-xtask)). rust-analyzer, cargo and zed use this form, and ruff and uv use the same idea under `cargo dev` ([rust-analyzer config](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/.cargo/config.toml), [zed config](https://raw.githubusercontent.com/zed-industries/zed/main/.cargo/config.toml)). After a fresh clone, `cargo xtask ci` runs fmt, clippy with `-D warnings`, the full test suite including the git oracle, the artifact leak check and a small digest-checked benchmark. It calls subprocesses only through `std::process::Command` with `env::var("CARGO")` and never builds shell strings. The core path depends on cargo and git, nothing else. The git CLI is already present wherever a clone exists, and xtask checks its version and fails with a clear message if git is missing. Extra tools (cargo-nextest, cargo-mutants, cargo-deny, gungraun) belong to `cargo xtask ci --full`. They are installed `--locked` at pinned versions under `target/tools`, so they never become a prerequisite or touch the user's environment. Per-process test isolation from nextest is no longer needed for correctness once environment reads are gone. `just` is rejected because it needs an `sh` on Windows ([just README](https://raw.githubusercontent.com/casey/just/master/README.md)), and Nix/devenv has no native Windows story. CI runs the same command on Windows, macOS and Linux runners. "Identically" here means the same commands, fixtures, seeds and expected digests. Timings will still differ by hardware.

Layering moves from grep into the compiler. `gitgraph-domain` (no gix, no IO), `gitgraph-support`, `gitgraph-adapters` and `gitgraph-application` become crates, so an illegal import fails to compile. Workspace `[lints]` set `unsafe_code = "forbid"`, `clippy.dbg_macro`, `todo` and `unimplemented` to deny, and `allow_attributes_without_reason` to deny ([Cargo lints](https://doc.rust-lang.org/cargo/reference/manifest.html), [Clippy configuration](https://doc.rust-lang.org/clippy/lint_configuration.html)). clippy `disallowed-methods` bans `std::env::var` outside the config module. It also bans `std::env::set_var`, `std::env::temp_dir`, `std::env::current_dir` and `std::fs::canonicalize`, which on Windows "converts the path to use extended length path syntax" ([std::fs::canonicalize](https://doc.rust-lang.org/std/fs/fn.canonicalize.html)); `dunce` replaces it. The typed `IngestConfig` is built once at the CLI or Tauri boundary and passed down. Tests construct their own configs, which removes the env-mutation race (item 9) and the Rust 2024 `unsafe set_var` blocker in the same move.

### The artifact contract: everything under target/, swept, and gated

Destructor cleanup alone cannot meet "never leave artifacts". `TempDir` cleanup fails when destructors do not run, as on unhandled signals ([tempfile](https://docs.rs/tempfile/latest/tempfile/)), and Windows refuses to delete files with open handles or mappings. The contract therefore has five parts. First, every test, benchmark and fixture artifact lives under `target/gitgraph-artifacts/run-<id>/`, via `CARGO_TARGET_TMPDIR` in integration tests and benches, which cargo creates "inside the target directory" ([Cargo env vars](https://doc.rust-lang.org/cargo/reference/environment-variables.html)), and via an explicit `--artifact-root` from xtask everywhere else. Second, each test creates `TempDir::new_in(run_dir)` and drops gix handles before the guard, so Windows deletes succeed. Third, xtask sweeps stale `run-*` directories at the start of every run, which recovers leaks from SIGKILL, timeouts and power loss. That is ripgrep's delete-before-create pattern made robust ([ripgrep tests/util.rs](https://raw.githubusercontent.com/BurntSushi/ripgrep/master/tests/util.rs)). Fourth, fixture git commands run with a pinned environment (`GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL` set to the null device, fixed author and committer dates), as gitoxide's test tools do ([gix-testtools](https://raw.githubusercontent.com/GitoxideLabs/gitoxide/main/tests/tools/src/lib.rs)). Tests then never read or write the user's git config or HOME. Fifth, a gate fails the build if, after the suite, `git status --porcelain --ignored` shows anything outside `target/`, if the run directory is not empty, or if the OS temp directory holds new project-prefixed entries. Large generated fixtures are deleted at the end of the run by default. They are kept only with an explicit `--keep-fixtures` (for repeated local perf work), and even then only under `target/`, where `cargo clean` removes them. One limit should be stated plainly. A hard kill can leave files under `target/gitgraph-artifacts/` until the next run's sweep or `cargo clean`. Nothing can land outside `target/`, and the leak gate makes any violation a failing build.

### A layered oracle that would have caught the edge loss

Two tests catch "edges dropped across batch boundaries" directly: a differential oracle against real git, and a metamorphic invariant that output must not depend on how ingestion was split. Seeded fixtures come from `git fast-import`, which builds repos from a text stream with explicit timestamps ([git-fast-import](https://git-scm.com/docs/git-fast-import)). The oracle compares canonicalized sets, never counts. Commits and ordered parent lists are checked against `git rev-list --all --parents` ([git-rev-list](https://git-scm.com/docs/git-rev-list)). Change sets are checked against `git log --raw -z --no-abbrev --no-renames --diff-merges=first-parent`, with exact equality on status, modes, OIDs and paths, and exact renames against `-M100%`. Similarity renames are reported, not gated. Ancestry is checked against `git merge-base --all` and `--is-ancestor` over random pairs. The fixture matrix covers octopus merges, multiple roots, empty commits, more than 512 changes in one commit, non-ASCII and invalid-UTF-8 paths, mode-only changes, symlinks, gitlinks, case-only renames, `--object-format=sha256`, shallow clones, `git replace`, `--filter=blob:none`, rebase + `gc --prune=now`, repack mid-ingest, and clock skew where a child predates its parent. proptest generates random DAGs, and batch size and thread count are generated parameters too. Shrinking reduces any failure to a minimal DAG plus batch size, and failing seeds persist as permanent regression files ([proptest](https://github.com/proptest-rs/proptest)). The metamorphic relations need no git. `ingest(batch=k)` must equal `ingest(batch=1)` for every k. Full ingest must equal prefix-then-rest ingest. Parallel must equal serial. The commit-graph path must equal the object-walk path. Every performance profile must equal the default. Windows must equal macOS must equal Linux. Each relation compares one **content digest**: a hash over OID-sorted records of `(oid, ordered parent oids, deterministic derived facts)`. That digest does not depend on IDs or layer boundaries, so it is cheap to compare across machines. cargo-mutants then shows whether the assertions bite. It finds "places where bugs can be inserted without causing any tests to fail" ([mutants.rs](https://mutants.rs/)). It runs `--in-diff` on PRs that touch `git.rs`, `db.rs`, `indexer.rs` and their successors ([mutants.rs in-diff](https://mutants.rs/in-diff.html)). A surviving mutant in batching code is the measurable signal that a tautology like `indexer_smoke.rs:85` has returned. Crash safety gets a fault-injecting writer that aborts between write, sync and rename. The test asserts that recovery always lands on the old or the new manifest. TigerBeetle's seeded VOPR shows the payoff of seed-reproducible faults ([TigerBeetle VOPR](https://raw.githubusercontent.com/tigerbeetle/tigerbeetle/main/docs/internals/vopr.md)). A full simulation runtime would be overkill for a single-process indexer.

### Perf gates that validate output before trusting a timer

A benchmark that does not check its output measures nothing, as `let _ =` in the current harness shows. Every perf scenario first computes the content digest and the query-result hashes, and compares them with the oracle-derived expected values for its seeded fixture. A mismatch is a hard failure before any timing is reported. Results pass through `std::hint::black_box`, and fixture generation happens outside the timed region. Per-PR gating uses instruction counts from gungraun (formerly iai-callgrind), which is consistent "even in" noisy environments ([gungraun README](https://raw.githubusercontent.com/gungraun/gungraun/main/README.md)). It runs on 5k–20k-commit meso benchmarks on Linux x86_64 and arm64 only, because Valgrind does not run on Windows or modern macOS ([Valgrind platforms](https://valgrind.org/info/platforms.html)). Wall time at 1M and 10M commits runs on a scheduled lane on fixed hardware, with a statistical threshold (Student's t-test or IQR, minimum sample size, `--error-on-alert`) ([Bencher thresholds](https://bencher.dev/docs/explanation/thresholds/)). On Windows and macOS, wall time is reported for information only. `perf-report` emits JSON (scenario, seed, generator version, digest, `digest_ok`, metrics) under `target/gitgraph-artifacts/perf/` and stops writing `tmp/perf-report-*.txt`. Benchmarks run the shipped default configuration, never a lane-specific env mix like `-HardwareMax`.

## Novelty: claim the verification contract, credit everything else

Every component of the blueprint is prior art, and the report says so. Topological integer IDs and segments come from Sapling's IdDag ([sapling-dag](https://docs.rs/sapling-dag/latest/dag/)). Segmented changelog already runs on plain git repositories: gitdag "maintains segmented changelog as an index on the Git commit graph" for git-branchless ([gitdag](https://docs.rs/gitdag/latest/gitdag/struct.GitDag.html)). A layered, parents-first index with global positions is jj's ([jj-lib readonly.rs](https://docs.rs/jj-lib/latest/src/jj_lib/default_index/readonly.rs.html)). Chunked, checksummed files, split chains with geometric merging, generation numbers and changed-path filters are git's ([gitformat-commit-graph](https://git-scm.com/docs/gitformat-commit-graph)). Immutable segments with an atomic metadata swap are Tantivy's ([Tantivy](https://github.com/quickwit-oss/tantivy/blob/main/ARCHITECTURE.md)). Recursive, versioned derived data is Mononoke's, now echoed in Anthropic's Scion, which added Mononoke credit after public criticism ([InfoQ, Oct 2026](https://infoq.com/news/2026/10/anthropic-source-control)). History-independent roots are Dolt's ([Dolt prolly trees](https://dolthub.com/blog/2024-03-03-prolly-trees)). Append-only consistency proofs are RFC 9162's ([RFC 9162](https://www.rfc-editor.org/rfc/rfc9162.html)). Compressed whole-history graphs are Software Heritage's and WebGraph's ([swh-graph SANER 2020](https://upsilon.cc/zack/research/publications/saner-2020-swh-graph.pdf)). A persistent local IDE git-log index is JetBrains' ([JetBrains VCS log settings](https://www.jetbrains.com/help/idea/settings-version-control-log.html.md)). Seeded deterministic simulation is TigerBeetle's. Claiming novelty for topological numbering, segments, layered immutable indexes, Bloom or fuse filters, derived data, compressed graphs or incremental computation would be refuted at once.

The defensible claim is narrow and falsifiable, and it covers a verification contract rather than a data structure. Suggested wording for the ADR: *"To our knowledge, FinalGitGraph is the first local git-history index whose logical content is a pure function of the reachable commit DAG and a format version, invariant to ingestion batching, parallelism, ingest path (commit-graph vs object walk) and host OS. That content is committed by a digest compared across all those variations in CI on Windows, macOS and Linux, and anchored to ground truth by differential tests against the git CLI. It builds on Sapling's segmented changelog, gitdag, jj's index, git's commit-graph, Mononoke's derived data, Dolt and RFC 9162."* The evidence for "first" is negative. About 45 queries and fetches found no Merkle-rooted, batch-invariant derived index for git analytics, and no project combining differential dataflow with git mining ([search result set](https://deepai.org/publication/tooling-for-time-and-space-efficient-git-repository-mining)). That is not proof of absence. Before any public claim, a dated search log should cover PVLDB/SIGMOD/CIDR, MSR/ICSE/FSE, authenticated-data-structure literature, the git mailing list, and the issue trackers of Sapling, jj and gitoxide. A digest proves determinism, not truth: deterministic garbage gets a stable digest, which is why the git oracle is mandatory. The stronger version holds two roots: a physical canonical root over byte-identical compacted layers, and an RFC 9162 chain root with consistency proofs between index versions. It is the most novel part, and the least valuable for a single-user desktop. Proofs matter only when indexes are shared, for example a CI-built index downloaded by clients. So it is deferred behind that trigger, not built into v1.

### Validation and kill criteria for the risky bets

Each risky choice gets a pre-registered test and a fallback. Thresholds are written into the ADR before measuring, so a result cannot move the goalposts.

| Risky choice | Validation | Kill criterion and fallback |
|---|---|---|
| Remove LMDB for immutable layers | Digest-checked ingest benchmark, old path vs layers, at 1M and 10M commits; crash-injection test; Windows CI for rename-while-open and delete-while-open | Layers miss the pre-registered throughput, or recovery ever lands on neither the old nor the new manifest: keep a KV engine (heed 0.23 on LMDB 1.0-dev ([heed](https://crates.io/crates/heed)), or redb) for the failing part only |
| No embedded DB in v1 | Inventory of mutable state at cutover | A mutable record set outgrows a manifest file or needs frequent small updates: add redb ≥4.4.0 with integrity checks in tests; SQLite WAL if redb fails them |
| `read()` instead of mmap | Cold-open time and RSS at 1M/10M on all three OSes | Open time exceeds the UI's cold-start budget: adopt memmap2 behind an `unsafe` ADR, never mapping files that can be replaced |
| Parent-first IDs + commit-graph bootstrap | Commit-graph path vs object walk digest on the fixture matrix | Any disagreement is an engine bug, not a tolerance; if the guards cannot be made exact, the object walk becomes the only path |
| Remove the tape walker | gix-pack vs tape, same digest | Keep the tape walker only if it beats gix-pack by the pre-registered margin |
| ≥100k commits/s | Topology+metadata and change-set throughput reported separately, on linux.git-sized and synthetic 10M DAGs | Topology misses 100k/s on the reference machine: profile before redesigning; change sets are never gated at 100k/s |
| Sapling-style segments (later) | Measure flat segments per commit on target repos | Segments/N > 0.3: keep CSR-in-layers with generation pruning only |
| Physical canonical root and consistency proofs (later) | Compaction cost at 10M commits | Exceeds the UI latency budget: compute in CI and background only, or keep the content digest alone |
| Tree-pair diff cache | Hit rate on real repos | Low hit rate: delete it |

## Conclusion

The edge-loss bug is the signature of the architecture, not a one-off slip. Once commits are numbered against the grain of the DAG, every optimization adds another place where an edge can fall between batches: the streaming delta, the overlay, the hardware-lane overrides, the 32 runtime switches. The tests could not see the result, because they compared the system with itself. The two decisive moves are cheap and independent of storage. First, make correctness structural: parent-first IDs, where a missing parent is a typed state, never a `continue`. Second, make it observable: a batch- and OS-invariant digest checked against `git rev-list`. Only after those two do performance work and the LMDB exit become safe, because any regression in either now fails a gate on all three operating systems.

The reform is mostly subtraction. It deletes LMDB, 17 tables, bincode on the hot path, the Bloom reader, the retry queue, most environment toggles and 4,191 lines of PowerShell, and the audit estimates about 1,500 fewer Rust lines on top. What it adds is small and borrowed: a git-style layer file, a manifest rename, an ID assigner and an oracle harness. The honest risks sit in a few places. Change-set extraction, not topology, will decide whether "100k commits/s" means anything beyond the graph. redb, mmap and segments are deferred until in-repo measurement shows they are needed. The novelty is real only as a verification contract, so it should be claimed that narrowly and with every prior system credited.
